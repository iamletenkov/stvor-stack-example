# stvor-stack-example

Шаблон репозитория для команды, которая доставляет Docker Compose-стек на роботы через портал Stvor. Стек из двух
сервисов — `api` (Python, только стандартная библиотека) и `web` (Node.js без зависимостей) — показывает весь путь:
сборка образов в CI, публикация релиза, назначение роботам, обновление и автоматический откат.

Скопируйте репозиторий («Use this template» или обычный клон), замените сервисы своими и оставьте конвейер выпуска.
Всё для выпуска уже в шаблоне, включая скрипт публикации `stvor-stack-publish.sh`. От портала нужны только стек и
ключ CI (шаги 1–3).

## Как устроен релиз

```text
тег v1.2.3 ─► CI: тесты ─► образы linux/amd64 + linux/arm64 ─► registry.<домен>/stacks/<слаг>/{api,web}:1.2.3
                                                                       │ digest манифеста каждой платформы
              файлы релиза на вариант (amd64, arm64) ◄─────────────────┘
              stvor-stack-publish.sh ─► POST https://<портал>/api/stack-ci/v1/releases ─► релиз «Доступен»
портал: назначение роботам ─► агент робота: pull по digest, docker compose up, окно проверки здоровья, при неудаче — откат
```

- **Стек** — единица назначения в портале, у него слаг (`demo`, `nav-stack`): раздел реестра `stacks/<слаг>/`.
- **Релиз** — одна версия (SemVer без `v`) одного **варианта**. Здесь вариант = архитектура: `amd64` и `arm64`, у
  каждого свой digest образов. CI публикует оба варианта версии одним запуском.
- На роботе ничего не собирается: агент скачивает образы только по digest и запускает `compose.yaml` релиза.
- Регистрация проверяет суммы файлов, синтаксис, переменные compose, наличие образов в реестре и порядок версий. Она
  ничего не устанавливает: релиз ставят роботам назначением.

Каталог релиза одного варианта (`dist/<arch>/` после `scripts/release.sh render`):

| Файл | Откуда |
|---|---|
| `compose.yaml` | `release/compose.release.yaml` с подставленными слагом, версией и digest образов |
| `parameters.yaml` | `release/parameters.yaml` — параметры и секреты, значения задаются при назначении |
| `CHANGELOG.md` | раздел текущей версии портал показывает на карточке релиза |
| `release.template.json` → `release.json` | `release/release.template.json`; поля версии, счётчика, времени, источника и образов заполняет `render`, а `__VARIANT__`, `__COMPOSE_DIGEST__`, `__PARAMETERS_DIGEST__` — `stvor-stack-publish.sh` |
| `SHA256SUMS` | пишет `stvor-stack-publish.sh` |

Файлы репозитория:

```text
api/, web/                  сервисы: код, тесты, многостадийный Dockerfile (build → test → runtime)
release/                    шаблоны compose.yaml, parameters.yaml и release.json
CHANGELOG.md                раздел на каждую версию — обязателен
scripts/release.sh          test, images, render, publish, all, local — одни шаги для CI и для человека
.github/workflows/release.yml   GitHub Actions: по тегу v* и вручную
.gitlab-ci.yml              self-hosted GitLab с Docker-раннером: только по тегу
demo/1.1.0.patch, 1.2.0.patch   изменения для сценария показа
stvor-stack-publish.sh      скрипт публикации — копия из портала, обновлять по шагу 2
```

### Что делает стек

`api` отвечает на `GET /healthz` и `GET /status`; `web` на `http://127.0.0.1:18080/` (на роботе — только localhost,
снаружи — через туннель Stvor) показывает версию, имя робота, цвет, приветствие, задан ли секрет и число запусков api.

| Имя | Что это |
|---|---|
| `DEMO_ROBOT_LABEL` | Параметр робота, обязательный, заполняется именем робота в Stvor (`autofill: robot.name`) |
| `DEMO_COLOR` | Параметр релиза, `blue` / `green` / `orange` / `purple` |
| `DEMO_GREETING` | Параметр релиза с умолчанием, появляется в 1.1.0 |
| `api_token` | Секрет робота, обязательный. Агент кладёт его файлом, compose подключает через `secrets:`, api читает `/run/secrets/api_token` и отдаёт только `true`/`false` — значение не выводится и не журналируется |
| `demo-data` | Именованный том: счётчик запусков `/data/start-count` переживает обновление и откат |

Оба сервиса работают от `10001:10001`, healthcheck — встроенными командами (`--healthcheck`), без curl в образе.

## Шаг за шагом

### 1. Создайте стек в портале

Нужно право «Стеки» в проекте (у владельца и лидов проекта оно есть всегда, участнику его выдаёт управляющий:
проект → «Участники» → колонка «Стеки»). «Стеки» → «Создать стек»: проект, наименование, слаг (2…40 знаков:
`a-z`, `0-9`, `-`). Слаг потом не меняется.

### 2. Получите ключ CI

Страница стека → вкладка «Публикация»:

1. «Ключи публикации» → «Выдать ключ» → вид «Ключ CI», метка, например `github-release`. Ключ `sck_…` показывается
   **один раз** — сразу перенесите его в секреты CI (шаг 3). Для ручного выпуска выдайте себе «Личный ключ» со сроком.
2. Скрипт публикации `stvor-stack-publish.sh` уже лежит в корне шаблона. Он один на все стеки и секретов не
   содержит; проверить его без сети — `sh ./stvor-stack-publish.sh --self-test` (CI делает это перед сборкой).
   Анонимной ссылки на скрипт нет, поэтому CI берёт его из репозитория. Обновился портал — «Скрипт публикации» →
   «Скачать скрипт», замените файл в корне и закоммитьте: версия скрипта должна совпадать с порталом.

Ключ стека пишет образы своего раздела реестра и регистрирует релизы этого стека. Он не может скачивать образы
(`docker pull` с ним не работает) и не может назначать релизы роботам.

### 3. Заведите переменные CI

Имена одинаковые для GitHub и GitLab; `stvor-stack-publish.sh` читает ключ **только** из переменной окружения
`STVOR_STACK_KEY`.

| Имя | Значение | Вид |
|---|---|---|
| `STVOR_URL` | `https://stvor.example.com` — адрес портала, без пути | переменная |
| `STVOR_STACK` | слаг стека | переменная |
| `STVOR_STACK_KEY` | ключ CI `sck_…` | секрет |
| `STVOR_COUNTER_OFFSET` | необязательно, см. «Счётчик релизов» | переменная |

**GitHub Actions.** Settings → Environments → создайте окружение `stvor-release`, в «Deployment branches and tags»
разрешите только теги `v*`, затем добавьте в нём секрет `STVOR_STACK_KEY` и переменные `STVOR_URL`, `STVOR_STACK`
(можно и на уровне репозитория: Settings → Secrets and variables → Actions). Ограничьте создание тегов `v*`
правилом (Settings → Rules → Rulesets). Окружение `stvor-release` указано в обоих заданиях workflow; если его не
создать, GitHub заведёт его при первом запуске — без ограничений. Workflow запускается только по тегу и вручную, у него только
`contents: read`; на pull request он не запускается, поэтому ключ не доступен коду из чужих веток.

**GitLab.** Settings → CI/CD → Variables: `STVOR_URL`, `STVOR_STACK`; `STVOR_STACK_KEY` — **Masked** и
**Protected**. Settings → Repository → Protected tags: `v*`, иначе задание по тегу не получит protected-переменную.
Нужен Docker-раннер с `privileged = true` (см. «GitLab: почему docker:dind»).

**Сеть раннера.** Раннер (GitHub-hosted или свой) должен доходить по HTTPS до `STVOR_URL` и до реестра
`registry.<хост портала>` — проверьте из сети раннера `curl -sI "$STVOR_URL/health"`. Портал на собственном CA —
см. «Частые ошибки».

### 4. Поставьте тег

```sh
git tag v1.0.0 && git push origin v1.0.0
```

Версия релиза — тег без `v`. В `CHANGELOG.md` должен быть раздел `## 1.0.0`, иначе выпуск остановится до
публикации. CI:

1. `scripts/release.sh test` — тесты в стадии `test` каждого Dockerfile, без сети;
2. `scripts/release.sh images` — `docker login -u ci` ключом (со stdin), `docker buildx build --platform
   linux/amd64,linux/arm64 --provenance=mode=max --push` в `registry.<хост портала>/stacks/<слаг>/<сервис>:<версия>`,
   индекс тега — в `dist/index-<сервис>.json`;
3. `scripts/release.sh render` — каталоги `dist/amd64/` и `dist/arm64/` (digest манифеста платформы из индекса);
4. `scripts/release.sh publish` — `stvor-stack-publish.sh --url … --stack … --version … --variant <arch> --dir
   dist/<arch>` на каждый вариант; ответ портала (JSON с `id`) — `dist/<arch>.response.json`.

Сборка и публикация — разные задания: если упала только публикация (сеть, 5xx), перезапустите **только её** —
она отправит те же байты и получит 200 с тем же id. Перезапуск сборки пересобирает образы — это уже другой релиз.
На GitHub ручной запуск («Run workflow») выбирайте на теге: с ветки workflow откажется.

### 5. Проверьте релиз

Отдельного одобрения релиза в портале нет: зарегистрированный релиз сразу «Доступен». Человеческий шлюз на пути
к роботу — назначение. Перед ним откройте карточку релиза и проверьте вкладки «Состав», «Параметры»,
«Совместимость и данные», «Файлы» и блок «Что изменилось» (раздел `CHANGELOG.md`). Ошибочный релиз — «Отозвать»
с причиной: его больше нельзя назначить.

### 6. Назначьте роботам

Карточка релиза → «Назначить»: вариант (по архитектуре робота), роботы, параметры («Общие параметры релиза» —
`DEMO_COLOR`; «Параметры роботов» — `DEMO_ROBOT_LABEL`, уже заполнен именем робота), секрет `api_token` (любое
непустое значение), «Окно проверки здоровья, с» (по умолчанию из релиза — 120). Назначать может обладатель права
«Стеки» в проекте робота. Ход — на карточке робота, вкладка «Стеки»: «Ожидает выхода на связь» → «Применяется» →
«Совпадает».

### 7. Обновите или откатите

- **Обновить** — новый тег, затем на роботе «Обновить» (или «Назначить» новый релиз). Именованный том сохраняется.
- **Изменить параметры** — новое назначение того же релиза, без нового тега.
- **Автоматический откат** — если за окно проверки здоровья хотя бы один сервис не стал `healthy` (или
  перезапустился, завершился), агент сам возвращает прежний релиз с его параметрами и секретами: «Откатился».
- **Ручной откат** — «Откатить» на роботе: выбрать более старый релиз и указать причину. Старый релиз ставится
  только так — обычное назначение откажет.
- **Снять** — агент остановит сервисы; тома и данные останутся.

## Сценарий показа: 1.0.0 → 1.1.0 → 1.2.0

Репозиторий в состоянии 1.0.0. Следующие версии — готовые изменения в `demo/`, их коммитят и помечают тегом, как
обычную работу:

```sh
git tag v1.0.0 && git push origin v1.0.0                     # 1.0.0: blue, без приветствия

git apply demo/1.1.0.patch                                  # новый параметр DEMO_GREETING с умолчанием,
git commit -am "feat: версия 1.1.0" && git tag v1.1.0       # умолчание DEMO_COLOR — green, раздел CHANGELOG
git push origin HEAD v1.1.0

git apply demo/1.2.0.patch                                  # healthcheck web опрашивает не тот порт
git commit -am "feat: версия 1.2.0 (сломанный healthcheck)" && git tag v1.2.0
git push origin HEAD v1.2.0
```

1. Назначьте 1.0.0 двум роботам, цвет `blue`, задайте секрет. Страница: версия 1.0.0, «Секрет api_token задан —
   true», «Число запусков api — 1».
2. Обновите на 1.1.0, цвет `green`: полоса меняет цвет, появляется «Приветствие» (умолчание `Hello, robot`,
   параметр можно не задавать), счётчик запусков растёт — данные в томе пережили обновление.
3. Обновите на 1.2.0: web не станет healthy, через 120 с агент вернёт 1.1.0 с её параметрами — на роботе
   «Откатился», причина `health_timeout`. Счётчик учитывает оба запуска.
4. Ручной откат на 1.0.0 с причиной — цвет и параметры 1.0.0.
5. После показа: `git revert HEAD`, раздел `## 1.2.1` в `CHANGELOG.md`, тег `v1.2.1`. Сломанный 1.2.0 отзовите.

## Выпуск без CI

Тот же конвейер руками (bash или zsh, из корня репозитория). Нужны Docker с buildx (builder
`docker buildx create --use`), `jq`, `curl`, `sha256sum`; ключ — личный, вводится скрыто:

```sh
export STVOR_URL=https://stvor.example.com STVOR_STACK=<слаг> VERSION=1.0.0
export RELEASE_COUNTER=<целое больше счётчиков прошлых версий>   # см. «Счётчик релизов»
export SOURCE_REPO=https://github.com/<организация>/<репозиторий>
printf 'Ключ стека: ' >&2; read -rs STVOR_STACK_KEY; echo >&2; export STVOR_STACK_KEY
scripts/release.sh all            # test, images, render, publish
unset STVOR_STACK_KEY
```

По шагам — `scripts/release.sh test|images|render|publish`. Повтор `publish` из того же `dist/` безопасен (200,
тот же id); `render` заново даёт новые байты, если изменилось время (`CREATED_AT`, по умолчанию — время коммита).

## Как проверить у себя

```sh
(cd api && python3 -m unittest -v) && (cd web && node --test)    # тесты без Docker
scripts/release.sh test                                         # те же тесты в стадии test Dockerfile
scripts/release.sh local                                        # сборка под свою архитектуру и запуск стека
```

`local` собирает образы с `--load`, подставляет их в compose вместо реестра, создаёт фиктивный секрет и
env-файл со служебными `STACK_*` в `dist/local/`, проверяет `docker compose config` и поднимает стек
(`up --wait --pull never --no-build` — как агент). Страница — `http://127.0.0.1:18080/`, остановка — командой из
вывода. `render` после подстановки тоже проверяет `docker compose config`. Это не заменяет проверок портала
(переменные, строгий YAML, образы в реестре) — их даёт публикация на тестовом стеке и назначение тестовому роботу.

## Чего нельзя

- **Секретов в репозитории, compose, образе, `CHANGELOG.md` и логах CI.** Секрет объявляется в `parameters.yaml`,
  значение вводится при назначении и приходит файлом. Секреты сборки — только `docker buildx build --secret`, не
  `--build-arg`: аргументы сборки попадают в аттестацию `--provenance=mode=max`.
- **Ключа стека в аргументах команд, YAML и `set -x`.** Только переменная `STVOR_STACK_KEY`; скрипты отказывают,
  если видят `sck_` в аргументах.
- **Тегов `latest` и переезжающих тегов.** Версия — неизменяемый тег, робот берёт образ по digest. Повторная
  публикация той же версии с другими байтами — 409. Пробные сборки в раздел стека не пушьте.
- **Сборки и загрузки кода при старте.** `build:` в compose агент отвергает; git clone, компиляция, `pip install`,
  скачивание моделей в entrypoint не допускаются — всё нужное уже в образе.
- **Монтирования исходников и файлов рядом с compose** (`./config`, `../src`, `${PWD}`): на роботе рядом с
  `compose.yaml` ничего нет. Конфигурация — в образе или параметрами; данные — именованные тома.
- **`include`, `extends`, `env_file`, верхнеуровневого `name`** в `compose.yaml` релиза; `privileged`, Docker-сокета,
  `/`, `/etc` хоста.
- **Базовых образов из реестра Stvor**: ключ стека не может `pull`, `FROM` берите из доступного команде источника,
  кэш BuildKit держите локально.

## Счётчик релизов

`release_counter` — целое ≥ 1: одинаковое у всех вариантов одной версии и строго больше, чем у любой другой версии
стека. CI берёт номер запуска (`github.run_number`, `CI_PIPELINE_IID`) плюс `STVOR_COUNTER_OFFSET`. Если стек
раньше выпускался из другого CI или вручную со счётчиком больше, задайте `STVOR_COUNTER_OFFSET` больше прежнего
максимума. Выпускайте версии по одному (workflow и задания сериализованы); исправление старой ветки после новой
версии тоже получает новый, больший счётчик.

## Время релиза

`created_at` в `release.json` — часть байтов релиза, поэтому оно фиксируется на этапе `render` и не меняется при
повторе публикации:

- **GitHub** — время коммита тега (умолчание `render`);
- **GitLab** — `CI_PIPELINE_CREATED_AT`, время создания pipeline. Это встроенная переменная GitLab вида
  `2026-11-25T12:00:00Z`; если она придёт со смещением или долями секунды, `render` приведёт её к UTC;
- **вручную** — время коммита `HEAD` или явное `CREATED_AT=2026-11-25T12:00:00Z`.

## GitLab: почему docker:dind

Задание сборки идёт в `docker:29-cli` с сервисом `docker:29-dind` (TLS, `DOCKER_HOST=tcp://docker:2376`), как в
примере из руководства Stvor: каждое задание получает свой чистый демон и свой builder buildx, учётка реестра
живёт в каталоге задания и исчезает с ним, раннер не хранит чужих образов и логинов. Нужен Docker-раннер с
`privileged = true` и общим `/certs/client` у задания и сервиса. Buildx на shell-раннере проще и быстрее (кэш между
запусками), но делит демон, кэш и `~/.docker` между проектами — подходит только для выделенного раннера одной
команды. Сборка arm64 эмуляции не требует: стадии build/test идут на платформе сборщика, в runtime-стадии нет `RUN`.
Если в вашем Dockerfile она появится, включите binfmt (строка в `.gitlab-ci.yml`; на GitHub QEMU уже настроен).

## Частые ошибки

| Симптом | Причина и что сделать |
|---|---|
| «Нет stvor-stack-publish.sh в корне» | Файл удалён из копии шаблона — верните его или скачайте в портале (стек → «Публикация» → «Скачать скрипт») |
| `CREATED_AT: ожидается UTC` | Время не в формате ISO 8601 — задайте `CREATED_AT=2026-11-25T12:00:00Z` или уберите переменную |
| Код 2, «задайте ключ… STVOR_STACK_KEY» | Секрет не передан заданию: на GitLab тег не защищён или переменная не Protected; на GitHub секрет в другом окружении |
| Код 4, 401/403 | Ключ отозван, выдан для другого стека, у личного ключа истёк срок или снято право «Стеки» |
| Код 3, `образа нет в реестре` | Образы не отправлены или удалены после удаления релиза — перезапустите сборку |
| 422 `stacks.release_counter_not_increasing` | Счётчик не больше прошлых версий — `STVOR_COUNTER_OFFSET` |
| 422 `stacks.release_counter_mismatch` | Варианты одной версии с разными счётчиками — выпускайте оба одним запуском |
| 409 `stacks.release_conflict` | Та же версия с другими байтами: перезапустили сборку вместо публикации — выпустите новую версию |
| 422 `stacks.undeclared_variable` | В compose (и в комментариях!) переменная не из `parameters.yaml` и не служебная `STACK_*`; для shell внутри контейнера — `$$VAR` |
| 422 `stacks.invalid_value` про digest | В `images` digest индекса, а не манифеста платформы — `render` берёт правильный, не правьте вручную |
| «в CHANGELOG.md нет раздела» | Добавьте `## <версия>` до тега |
| На роботе «Откатился», `health_timeout` | Сервис не стал healthy за окно: healthcheck, порт, `start_period`, права тома |
| `x509: certificate signed by unknown authority` | Портал на собственном CA: доверьте его dind/buildx и задайте `CURL_CA_BUNDLE` |
| Push: `blob unknown to registry` | `images` повторяет push один раз; второй отказ — сообщите администратору Stvor |

Подробное руководство по стекам — в документации вашего экземпляра Stvor («Как выпустить стек в Stvor»).
